Quorum: a distributed key-value database built from scratch in Go

No Raft library, no embedded database, no consensus service. The storage engine and the consensus implementation are the project, and every guarantee the documentation states is bound to a test that checks it. The defining problem is integrating the durable LSM engine with the replicated state machine without weakening the guarantees already proven.

Overview

What it is

A replicated, sharded key-value store with exactly three operations on opaque byte keys and values: PUT, GET and DELETE. Keys are at most 4 KiB, values at most 1 MiB. There are no transactions, range scans, secondary indexes or multi-key atomicity. That restriction is deliberate: it is what makes the consistency claim defensible.

A client talks to any node over a framed binary TCP protocol. The node routes the key to its shard, the shard to its Raft group, and the request to that group's leader (forwarding one hop if it is not the leader itself). A write is acknowledged only once it is committed and applied in the term it was proposed in; a read is served through Raft's ReadIndex, never from a stale leader's local state. The documented model is linearizable single-key operations, per Raft group, verified on recorded histories rather than asserted (CONSISTENCY.md, LINEARIZABILITY.md).

Why build consensus and storage from scratch

Because the point is to own the correctness argument end to end. Raft, the durable log, crash recovery, snapshots, membership, the LSM engine (WAL, memtable, SSTables, Bloom filters, compaction, MANIFEST), the client protocol and the deduplication of retried requests are each implemented independently, then connected, in the order in which the next layer can be tested honestly: storage before networking, networking before replication, fault injection immediately after Raft, snapshots only after consistency testing (ROADMAP.md).

Intended use

A reference implementation and an engineering exercise: something another engineer can read, run on a laptop, break with the included fault tools, and check against its own invariants. It is explicitly not production-ready and has never run in production.

The one rule the project applies everywhere

Never claim a guarantee that has not been verified. Every guarantee maps to a numbered invariant in INVARIANTS.md, and every invariant names the test that checks it. Of the 125 invariants, two are still marked PLANNED and one is structural; a planned invariant may not be cited as a guarantee anywhere else. The things the system cannot do are enumerated in LIMITATIONS.md, and the engineering roadmap is an audit of the system as built, with its verified defects listed and ranked.

Architecture: the real path of a request

The diagram shows what dkvd actually runs today, package by package. Solid boxes are on every request's path; the dashed box is the LSM-backed state machine, which exists and passes every correctness tier but is opt-in (-state-machine lsm) while the in-memory machine remains the default. There is no HTTP API, dashboard or rebalancing: those are design only.

The same flow in words, with the code that does it

  1. Client request. A client opens a plain TCP connection to a node's -client-listen port and sends one checksummed frame: op, group, client ID, request ID, acknowledgement watermark, timeout, key and (for PUT) value. No HTTP, no TLS, no authentication. API.md · kv/wire.go
  2. Shard routing and group selection. The key is hashed (SHA-256, first 8 bytes) to a token; a consistent-hash ring over the fixed shard set maps it to a shard, and in -cluster mode group id equals shard id. A node that does not lead the group forwards the request one hop over the internal transport, or answers NOT_LEADER with a hint. ROUTING.md · MULTI_RAFT.md · kv/front.go
  3. Replication and commit. The group's server proposes the command to the Raft driver. The driver appends it to the durable log and fsyncs before anything is sent, replicates it with AppendEntries over the framed transport, and commits it when a majority has it, following the Raft §5.4.2 rule. The core itself performs no I/O and reads no clock, so the whole algorithm is also run inside a deterministic simulator. RAFT.md · raft/raft.go · raftnode/node.go
  4. State machine application. Committed entries are applied in log order. The replicated state is the key-value map plus a bounded session table that decides, identically on every replica, whether an identified write executes or is a duplicate of an earlier one. By default this state lives in memory (kv.Store); with -state-machine lsm it lives in the storage engine, one apply batch per Raft cycle, with the applied index recorded atomically in the engine's MANIFEST. DEDUP.md · kv/store.go · kv/lsm.go
  5. Persistence, snapshots and recovery. Every -snapshot-every applied entries a node writes its state to a versioned, checksummed snapshot file, publishes it by atomic rename, then compacts the Raft log behind it by an atomic rewrite. A follower too far behind installs the leader's snapshot, streamed in 1 MiB chunks. At start, recovery reconciles the log, the snapshot and (in LSM mode) the engine's durable applied index, refusing any contradiction; a failed persist stops the node rather than continuing in doubt. SNAPSHOTS.md · CRASH_RECOVERY.md · internal/snapshot

Subsystems, matched to what is implemented

Each card says what the component does, how it is verified, and where to read the exact claim. The figures are the ones the documents and the CI logs state for main.

  • Raft consensus implemented

    A pure, deterministic core: randomized election timeouts from an injected source, RequestVote and AppendEntries with a term-based conflict hint, the §5.4.2 commit rule and the mandatory election no-op, ReadIndex for reads. A durable log and HardState make it crash-safe; a node driver runs a real group over TCP, persisting before it replies.

    Evidence: INV-R1..R10 checked after every event of seeded, replayable simulations; the paper's figures reproduced as tests; real three-process election and SIGKILL recovery. RAFT.md · internal/raft

  • Replication and transport implemented

    One framed, checksummed TCP connection per peer pair (the lower id dials), a version handshake carrying the cluster id and a digest of the replicated settings, automatic reconnect, and a group envelope on every frame. The transport carries bytes tagged with a kind and knows nothing of terms or leaders; faults are injected around it, never inside the core.

    Evidence: INV-T1..T6; real-process partition, kill and freeze tests through TCP proxies. TRANSPORT.md · FAULTS.md

  • Crash recovery implemented

    Named crash points at every boundary of the driver's persist → send → advance → apply cycle and between the record writes of one durable-log save. A bounded exhaustive matrix kills a node at every point a scenario reaches, in every crash mode, and checks each recovery against an independent record of what was persisted. Real processes kill themselves at the exact point with dkvd -crash-at.

    Evidence: three crash matrices of 1,440, 2,976 and 6,660 cells (node, snapshot and membership windows), 0 failures; the save-order window that bricked a node was found and fixed. CRASH_RECOVERY.md

  • Snapshots and log compaction implemented

    The replicated state, session table included, in a versioned, deterministic file of CRC-32C records with a SHA-256 over the state and nothing after the footer. Published by atomic rename, then the log is compacted behind it by an atomic rewrite. Followers whose entries are gone install the leader's snapshot in 1 MiB chunks; recovery reconciles snapshot and log and refuses every contradiction.

    Evidence: a 2,976-cell crash matrix over every snapshot window; ten real-process tests including a SIGKILL mid-install; 100,000 writes, then a restart that replays 1 entry instead of 100,001. SNAPSHOTS.md

  • Membership and multi-Raft implemented

    A group adds a learner, promotes it and removes voters, the leader included, one member at a time by Raft §6 joint consensus, with the configuration carried as replicated state in the log and the snapshot. A node hosts one Raft group per shard it serves, each with its own log, snapshot, identity file and state machine; clients hold one session per group. Changes are operator-driven through the admin protocol.

    Evidence: INV-MB1..MB10 at every event of 200-seed schedules, a bounded model of every four-step sequence, a 6,660-cell crash matrix, ten real-process tests. MEMBERSHIP.md · MULTI_RAFT.md

  • Client semantics and deduplication implemented

    A client registers a session (its ID is the log index of the REGISTER entry) and numbers its requests. The state machine decides at apply, identically on every replica, whether an identified write executes or is a duplicate answered with the original's index. Retried identified writes execute at most once; anonymous writes keep the plain semantics. Nothing is claimed across groups.

    Evidence: the hardest retry case at all eight crash windows of a real process; 1,200 seeded runs in which every replica's apply-time decision matches an independent model. CLIENT_SEMANTICS.md · DEDUP.md

  • Linearizability checking implemented

    A checker, validated first against an independent oracle, a known-good and known-bad corpus and fuzzing, checks client histories recorded from real processes under faults, from the in-process driver, and from thousands of seeded simulator runs. A failing test leaves its history as an artifact that lincheck re-checks, minimizes and explains offline.

    Evidence: INV-X1..X14; 1,400 seeded runs for the base model and 1,200 for request identity. LINEARIZABILITY.md · internal/lincheck

  • LSM storage engine implemented

    Write-ahead log with CRC records, segmentation and torn-tail repair; an ordered memtable; immutable checksummed SSTables with Bloom filters; size-tiered compaction; a MANIFEST that decides which files are the database, so a file is part of it at exactly one instant. Acknowledged writes survive SIGKILL, including a kill during a flush or a compaction.

    Evidence: INV-W, INV-L, INV-B, INV-C and INV-M families; real-process kill tests that fail if the crash window was never hit. Standalone benchmarks in BENCHMARKS.md. LSM.md · WAL.md · MANIFEST.md

  • Fault injection and chaos implemented

    A deterministic simulator drives the real core, the real durable log on a crash-modeling disk and the driver's own ordering through seeded schedules of dropped, duplicated, delayed and reordered messages, partitions, crashes, modeled power loss and disk failures, checking every invariant after every event. Real processes are killed, frozen, partitioned and crashed at chosen points under a recorded workload that is then checked for linearizability.

    Evidence: make faults with 200 seeds in CI; make chaos; the simulator found and fixed three real bugs, one of which let a restarted node acknowledge entries a power loss could erase. FAULTS.md · CHAOS.md

  • Observability and operations implemented

    Every node serves Prometheus-format metrics from every layer on -metrics-listen, each incremented where the event happens and verified against ground truth. dkvctl reads the JSON-lines admin protocol for status, leaders, configurations, lag, health and readiness, with exit codes a probe can branch on. Nothing aggregates, stores or alerts on any of it.

Storage integration: where the flagship work stands

The engine and the replicated state machine were built separately. Making the LSM engine the state machine, without weakening any guarantee already proven, is organised as six milestones in STORAGE_INTEGRATION.md. The rule applied throughout: Raft decides order; the engine makes the result of applying that order durable; the engine never invents an order of its own.

MilestoneWhat it establishesState on main
S1 Atomic apply batchesA Raft cycle's mutations and its applied index are recorded in the engine as one unit (rule R1), proven in isolation by a deterministic crash and power-loss matrix over a modeled disk.merged
S2 The engine behind the state-machine interfacedkvd -state-machine lsm: each group's state in the engine under its directory, sessions under a reserved key tag, one apply batch per Raft cycle, recovery from the engine's applied index. Every linearizability, dedup, snapshot, membership and chaos tier passes on both machines.merged
S3 Durable watermarksThe applied index and last sequence are authoritative in the MANIFEST; the WAL is truncated behind each flush; the Raft log is never compacted past the engine's durable applied index (rule R2).merged
S4 Engine checkpoints and streamed installsSnapshots taken from a pinned engine checkpoint and installed by streaming into the engine, removing the ~63 MiB one-record install limit.in review, PR #27
S5 The two-log measurementWhether the Raft log and the engine's WAL should stay two logs, decided by measurement (ADR-006).planned
S6 Snapshot work off the actorMoving snapshot creation and the engine flush off the Raft node's actor, where today they pause Raft processing and can cost a leader its term under fsync-heavy load.planned

What this means in practice. On main the in-memory machine is the default and the LSM-backed machine is opt-in. Both pass the same correctness tiers. The LSM path is not yet the recommended configuration: its snapshots are bounded in size until S4 merges, and the actor-bound snapshot flush (S6) is a measured liveness cost. Nothing on this page describes S4–S6 as done.

What it does not. Storage engine, standalone

BENCHMARKS.md characterises the engine on its own with a reproducible harness (cmd/dkvbench, raw results in bench/phase5-baseline.json). Two figures the README keeps because they are properties of the algorithm rather than of the machine: with the Bloom filters on, 4,000 lookups over 17 SSTables read 2,395 data blocks instead of 52,329 (95.4% avoided, at 10.00 bits per key); and a device-level flush per write costs roughly 700× a buffered append (an early measurement: about 258 appends/s in sync mode against about 183,000 in the default batch mode), which is the honest price of power-loss durability and why batch is the default.

Quick start

Requires Go 1.27.2 or later (go.mod pins the patch release; with the default GOTOOLCHAIN=auto an older Go 1.27 fetches it). Everything below runs on one laptop.

Clone, build, run the gate

git clone https://github.com/adivishall/quorum.git
cd quorum
make build          # every command into bin/
make check          # gofmt, .gitignore guard, go vet, every unit package under -race: the phase gate
make integration    # real-process tests (several minutes)
make faults         # the deterministic fault schedules and crash matrices at 200 seeds

Slower tiers: make mutation, make fuzz, make chaos. The Makefile documents each.

A three-node cluster on your machine

Three dkvd processes on loopback, one Raft group per shard (4 shards, replication factor 3), the default in-memory state machine. The first start of each node initialises its data directory; every later start omits -init. Add -state-machine lsm to every node to run the LSM-backed machine instead; the flag is part of the replicated state machine's definition and must match on every node.

go build -o bin/ ./cmd/dkvd ./cmd/dkvctl ./cmd/dkvload
export PATH="$PWD/bin:$PATH"
mkdir -p data logs

dkvd -id n1 -listen 127.0.0.1:7001 -peers n2=127.0.0.1:7002,n3=127.0.0.1:7003 -data-dir data/n1 \
     -init -cluster-id demo -cluster -shards 4 -rf 3 \
     -client-listen 127.0.0.1:8001 -admin-listen 127.0.0.1:9001 -metrics-listen 127.0.0.1:9101 >logs/n1.log 2>&1 &
dkvd -id n2 -listen 127.0.0.1:7002 -peers n1=127.0.0.1:7001,n3=127.0.0.1:7003 -data-dir data/n2 \
     -init -cluster-id demo -cluster -shards 4 -rf 3 \
     -client-listen 127.0.0.1:8002 -admin-listen 127.0.0.1:9002 -metrics-listen 127.0.0.1:9102 >logs/n2.log 2>&1 &
dkvd -id n3 -listen 127.0.0.1:7003 -peers n1=127.0.0.1:7001,n2=127.0.0.1:7002 -data-dir data/n3 \
     -init -cluster-id demo -cluster -shards 4 -rf 3 \
     -client-listen 127.0.0.1:8003 -admin-listen 127.0.0.1:9003 -metrics-listen 127.0.0.1:9103 >logs/n3.log 2>&1 &

# Health, leaders and configurations, over the admin protocol (exit 0 = healthy).
dkvctl -nodes n1=127.0.0.1:9001,n2=127.0.0.1:9002,n3=127.0.0.1:9003 health
dkvctl -nodes n1=127.0.0.1:9001,n2=127.0.0.1:9002,n3=127.0.0.1:9003 status

# A real client workload through the binary client protocol.
dkvload -endpoints n1=127.0.0.1:8001,n2=127.0.0.1:8002,n3=127.0.0.1:8003 \
        -shards 4 -rf 3 -nodes n1,n2,n3 -clients 4 -rate 100 -duration 5s -read 50

# One node's metrics.
curl -s http://127.0.0.1:9101/metrics | grep -E '^dkv_raft_role'

The client protocol has no command-line client yet (bin/dkv is an in-memory CLI from Phase 1, not a network client). dkvload is the supported way to put real requests through a cluster from the shell; the Go client library is kv.Client and kv.Session in internal/kv.

Limitations, stated plainly

From LIMITATIONS.md, which keeps the full list with the reason for each.

Not production-ready. The project's own words: this system has not run in production, has no operational tooling, no backup/restore, no upgrade path, no security model, and no track record. It is an engineering exercise built to be correct and explainable, not to be deployed.

  • Every port is unauthenticated plaintext TCP. Anyone who reaches the client port can read, write and delete any key; the admin port can remove voters and stop groups, which is why it binds to loopback unless -admin-allow-remote is given. There is no TLS and no identity beyond a protocol label.
  • Power-loss durability is untested on a real device, in every mode. The crash tests destroy a process with SIGKILL, which proves bytes reached the kernel, not the platter; power loss exists only as a software model.
  • Linearizability is verified on recorded, finite histories, not proven for every execution, and only per Raft group; nothing is claimed across groups.
  • No PreVote or CheckQuorum. A leader cut off from its peers keeps accepting requests it can never complete until its clients' deadlines expire, and a rejoining partitioned node forces one extra election.
  • The replicated state machine is in memory by default. The LSM-backed machine is opt-in and its snapshots are size-bounded until S4 merges.
  • An LSM leader flushes its engine at every snapshot on its Raft actor, which under fsync-heavy load was measured to cost it its term in 7–10 of 60 runs. S6 moves that work off the actor.
  • WAL segment and SSTable numbers are six digits and never reused, so a node under sustained load runs out after weeks, then fail-stops without loss. Tracked as #20.
  • Routing is fixed at bootstrap and must be identical on every node; there is no rebalancing, no data movement between groups, and membership changes are operator-driven, one member at a time.
  • Concurrent writes share nothing yet: every write costs its own fsync, which is what the cluster baseline measures and what layer 3 exists to change.
  • Metrics are per node, pull-only and in memory; nothing aggregates, stores or alerts.

Open follow-ups are tracked as GitHub issues: file-number exhaustion (#20), an intermittent read rejection seen once on CI (#21), the actor-bound snapshot flush (#22) and queued snapshot-frame memory (#24), among others.
