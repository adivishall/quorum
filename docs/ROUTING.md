# ROUTING — consistent-hash sharding (Phase 6)

Status: **implemented and verified (Phase 6).** This document specifies the routing
layer precisely enough to reproduce every number in it by hand, and binds each guarantee
to a test in `internal/routing`. It is the reference for `internal/routing`, `cmd/dkvring`,
ADR-012, and invariants INV-C1/C2/C3 (`docs/INVARIANTS.md`, "Routing / cluster").

Routing is a **pure deterministic library**. It imports nothing from `internal/storage`,
`internal/raft`, `internal/transport`, `internal/cluster`, no networking package, no clock,
and no global randomness. A route is a function of `(key, configuration)` and nothing else,
so the same inputs produce the same shard on every machine, forever (INV-C1).

What Phase 6 does **not** do is as important as what it does — see §9.

---

## 1. The pipeline

```
key (opaque bytes)
   │  sha256, first 8 bytes, big-endian
   ▼
64-bit token
   │  successor lookup on the SHARD ring
   ▼
ShardID                         ← Route(key); INV-C1, INV-C2
   │  shard anchor → successor walk on the NODE ring
   ▼
replica group  [primary, …]     ← declarative metadata; INV-C2, INV-C3
   │
   ▼
future Raft group (Phase 8+, NOT built here)
```

Two rings, one immutable `Config`. The **shard ring** turns a key into a shard and depends
only on the shard count, so it never moves when nodes come and go. The **node ring** turns a
shard into an ordered list of nodes (its replica group) and is where a membership change
redistributes work. Splitting them is the whole design; the reasoning is ADR-012.

---

## 2. The token: SHA-256 → 64-bit

```
token(b) = binary.BigEndian.Uint64( sha256(b)[:8] )
```

- **SHA-256** of the input bytes, then the **first 8 bytes** of the 32-byte digest,
  interpreted **big-endian** as a `uint64`.
- Big-endian matches the internal-key sequence encoding (`docs/DESIGN.md` §1). "First 8
  bytes" is the simplest fully-specified selection; SHA-256's output is uniform, so any fixed
  8-byte window is uniform and no window is more correct than another — it just has to be
  pinned, and it is pinned here and in a golden test.
- The input is hashed as **opaque bytes**: no normalisation, no case folding, no trimming,
  no UTF-8 interpretation (INV-A5). The empty key, NUL bytes, and invalid UTF-8 are all valid
  routing inputs. Key *validation* (size limits, empty-key rejection) belongs to the storage
  and API layers, not here — routing is total over `[]byte`.

The empty string is the standard SHA-256 test vector, which is a free sanity check that the
rule is ordinary SHA-256:

```
token("")                         = 0xe3b0c44298fc1c14   (sha256("") = e3b0c442 98fc1c14 …)
token("user:123")                 = 0x61b7de306ccf11d6
token("\x00")                     = 0x6e340b9cffb37a98
token("\xff\xfe\xfd\x00\x01")     = 0x491865266935dcc5
token("The quick brown fox")      = 0x5cac4f980fedc3d3
token("\x00\x00\x00\x00\x00\x00\x00\x00") = 0xaf5570f5a1810b7a
```

### Virtual-node and anchor tokens

Ring positions are derived with the same `token(...)` rule over a structured label. The `i`
suffix is fixed-width and last, which makes each label injective in its inputs:

```
shardVnodeToken(shard, i) = token( "DKVSHARD\x00" || be32(shard) || be32(i) )
nodeVnodeToken(nodeID, i) = token( "DKVNODE\x00"  || nodeID     || be32(i) )
anchorToken(shard)        = token( "DKVANCHOR\x00" || be32(shard) )
```

`be32` is 4-byte big-endian. `nodeID` is the raw bytes of the node's identifier. The ASCII
prefixes (`DKVSHARD\x00`, `DKVNODE\x00`, `DKVANCHOR\x00`) separate the three namespaces so a
shard vnode can never collide with a node vnode by construction of the label.

## 3. The ring

A ring is a slice of positions, each `{token, ownerID, vnodeIndex}`, **sorted once at
construction** by `(token, ownerID, vnodeIndex)` ascending. Construction never depends on Go
map iteration order — the positions are generated by iterating owners and vnode indices in
numeric order and then sorted, so two configurations with the same members in any input order
build a byte-identical ring.

**Lookup (successor, clockwise).** For a query token `T`, the owner is the position with the
smallest token `≥ T`, found by binary search — `O(log P)` over `P` positions. If no position
is `≥ T` (the token is past the largest position), the lookup **wraps** to index 0. This is
the ring closing on itself.

**Boundary rule.** A position `P` owns the half-open arc `(predecessor, P]`. A key whose token
equals a position exactly is owned by that position (the successor comparison is `≥`, i.e.
inclusive at the boundary). Every token in `[0, 2⁶⁴)` is owned by exactly one position, and
adjacent positions' arcs are disjoint and cover the whole ring including the wrap arc — this
is the coverage INV-C2 asserts.

**Token collisions.** Two virtual nodes may hash to the *same* 64-bit token. This is a legal,
deterministic case, not an error: the `(token, ownerID, vnodeIndex)` sort key breaks the tie,
so the position with the smaller owner id (then smaller vnode index) sorts first and a
successor landing on that token returns it. A collision changes which owner wins a
vanishingly thin arc; it never leaves a token unowned or doubly owned. This is distinct from a
duplicate node **identity**, which is rejected (§6).

## 4. `Route(key) → ShardID` (the shard ring)

The `ShardCount` shards are each placed at `VNodesPerShard = 128` positions on the shard ring
(`shardVnodeToken(shard, i)` for `i` in `[0, 128)`). `Route(key)` computes `token(key)` and
returns the shard owning the successor position.

- Deterministic and pure: depends only on `(key, ShardCount)`.
- **Stable across node membership changes.** The shard ring does not mention nodes, so adding
  or removing a node changes no key's shard. This is exactly what "fixed shard count" means,
  and INV-C3's test asserts it (zero shard changes on a node change).
- A real ring, not `token % ShardCount` — honouring `docs/ARCHITECTURE.md` §4 and keeping the
  shard sizes uniform through virtual nodes. `ShardCount = 1` is legal and routes every key to
  shard 0.

Golden routes for `ShardCount = 16` (the v1 default), reproducible from §2:

```
key                     → shard
""                      → 8
"user:123"              → 6
"\x00"                  → 6
"\xff\xfe\xfd\x00\x01"  → 3
"The quick brown fox"   → 11
"\x00"×8                → 1
```

## 5. Shard → replica group (the node ring)

The `Nodes` are each placed at `VNodesPerNode = 128` positions on the node ring. Each shard
has a single **anchor** token (`anchorToken(shard)`); walking the node ring clockwise from the
anchor and collecting the first `ReplicationFactor` **distinct** node IDs yields the shard's
**replica group**, an ordered list whose head is the **primary**.

This list is **declarative metadata**. Phase 6 computes *who* would own each shard; it does not
replicate, elect, or move any data (§9, ADR-001/005). The primary is what INV-C3 tracks across
membership changes.

Golden replica groups for `Nodes = [n0, n1, n2]`, `RF = 3`, `ShardCount = 16` (reproducible
from §2's anchor rule):

```
shard  0 → [n1 n0 n2]      shard  8 → [n0 n2 n1]
shard  1 → [n0 n1 n2]      shard  9 → [n0 n1 n2]
shard  2 → [n1 n2 n0]      shard 10 → [n0 n2 n1]
shard  3 → [n1 n2 n0]      shard 11 → [n0 n2 n1]
shard  4 → [n2 n1 n0]      shard 12 → [n0 n2 n1]
shard  5 → [n2 n0 n1]      shard 13 → [n1 n2 n0]
shard  6 → [n0 n2 n1]      shard 14 → [n1 n2 n0]
shard  7 → [n1 n2 n0]      shard 15 → [n0 n2 n1]
```

Every group has exactly `min(RF, len(Nodes))` distinct nodes, and every shard has exactly one
group — INV-C2.

## 6. Configuration and failure behaviour

`Config` is `{ShardCount int, ReplicationFactor int, Nodes []NodeID}`, validated once when a
`Router` is built. Every invalid input fails explicitly with a typed `*ConfigError` wrapping a
sentinel (`errors.Is`-testable). Nothing is silently repaired, reordered in an undocumented
way, dropped, or invented.

| Condition | Result |
|---|---|
| `ShardCount < 1` or `> MaxShardCount` (4096) | `ErrInvalidShardCount` |
| `ReplicationFactor < 1` | `ErrInvalidReplicationFactor` |
| `ReplicationFactor > len(Nodes)` | `ErrInvalidReplicationFactor` (cannot place more distinct replicas than nodes) |
| `len(Nodes) == 0` | `ErrNoNodes` (an empty ring is never valid routing) |
| an empty node ID | `ErrEmptyNodeID` |
| a duplicate node **identity** | `ErrDuplicateNode` (never de-duplicated) |
| duplicate ring **position** (token collision) | not an error — resolved by the tie-break (§3) |
| unknown serialized config version | `ErrConfigVersion` |

`MaxShardCount` exists so a typo (`ShardCount = 1e9`) is a clear error rather than an
out-of-memory: the default is 16, and 4096 is far beyond any v1 need while keeping the ring
bounded. `Route` on a successfully-built `Router` never returns an error and never panics for
any `[]byte`, including nil and empty.

Nodes are sorted and de-duplicated-checked at construction, so routing is independent of the
order nodes were supplied in. `Config.Canonical()` produces deterministic, **versioned** JSON
(`{"version":1,"shard_count":…,"replication_factor":…,"nodes":[…sorted…]}`); `ParseConfig`
reconstructs it, and a router built from the parsed config routes identically (INV-C1).

## 7. Membership change and redistribution (INV-C3)

Runtime membership is static (ADR-005). A "membership change" in Phase 6 is therefore the
construction of a **new** `Config` with a node added or removed, compared against the old one —
never a mutation of a live router. This is exactly how the redistribution test is written.

Adding one node to an `N`-node ring reinserts that node's `VNodesPerNode` positions and steals
only the arcs immediately preceding them; every shard whose anchor falls elsewhere keeps its
primary. The expected fraction of shards that change primary is `≈ 1/(N+1)` (the new node's
share of the ring), against `≈ (N-1)/N` for the `shard % N` anti-pattern.

Because a shard's key space moves as a unit, two properties are asserted:

1. **Exact attribution (tolerance-free).** A key's owning node changes **iff** its shard's
   primary changed, and its shard never changes. Movement is fully explained by shard-primary
   reassignment, not by any key-level reshuffle.
2. **Principled bound vs modulo.** Measured deterministically at `ShardCount = 512` so the
   statistics are clean (the numbers below are fixed, not sampled):

   | change | ring shards moved | ≈ S/N expected | `shard % N` moved | of S |
   |---|---|---|---|---|
   | add a 4th node to 3 | 141 | 128 | 383 | 512 |
   | remove the 4th node from 4 | 141 | 128 | 383 | 512 |
   | add a 6th node to 5 | 68 | 85 | 425 | 512 |

   The ring moves within `[0.5, 2]×` of `S/N` and **far** less than modulo; the test asserts
   both the band and `ring_moved · 2 < modulo_moved` (the observed factor is ≈ 2.7 ≈ N−1),
   which is what distinguishes *expected movement* from a *total reshuffle*. With only 16 shards
   the movement is quantised to whole
   shards, so INV-C3 is stated at `ShardCount = 512` and the 16-shard default inherits the
   property by the same construction.

## 8. Visualization

`cmd/dkvring` renders a ring from a real `Router` — never a hard-coded illustration — in two
deterministic formats:

- **SVG** (`-format svg`): the token space drawn as a circle, shard ownership as coloured
  arcs, node positions as labelled marks, wrap-around visible as the arc crossing the top
  (token 0), and a legend listing the membership and each shard's replica group. No timestamps,
  no map iteration, fixed number formatting — rendering the same config twice is byte-identical
  (asserted by a test).
- **Text** (`-format text`): an ASCII summary — the sorted shard-ownership arcs, the node ring
  positions, and the shard→replica-group table — for terminals and CI diffs.

```
go run ./cmd/dkvring -shards 16 -rf 3 -nodes n0,n1,n2 -format svg  > ring.svg
go run ./cmd/dkvring -shards 16 -rf 3 -nodes n0,n1,n2 -format text
```

Both are generated straight from the `Router`'s ring structures, so they cannot drift from what
`Route` actually does.

## 9. What Phase 6 is NOT

Stated plainly so nobody upgrades the language later. Implemented now:

- deterministic `key → shard` routing (a consistent-hash ring, not modulo);
- a fixed, configurable shard count (default 16);
- a node ring producing declarative `shard → replica group` metadata;
- inspectable, versioned configuration;
- ring visualization (SVG + text).

**Not implemented, and not claimed, by this phase:**

- runtime membership changes / dynamic join-leave (ADR-005) — a "change" here is a new `Config`;
- replica management, data movement, or shard rebalancing — the group is a list of names;
- Raft, leader election, or any consensus (Phase 9);
- node-to-node communication, request forwarding, or an HTTP surface (Phase 7, 15);
- replication, fault tolerance, cluster availability, linearizability across nodes, or leader
  routing. Routing existing does not make any of these true. They belong to later phases and
  are tracked in `docs/CONSISTENCY.md` and `docs/LIMITATIONS.md`.

The replica-group metadata is the one place that could be misread as "replication exists." It
does not. It is a deterministic answer to "which nodes *would* own this shard," computed so
that Phase 8 has a correct assignment to build on.
